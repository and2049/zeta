# Built-in tools

- `read`: file path, optional one-based `offset` and `limit`. A PNG, JPEG, GIF or WebP file (up to 4 MB) comes back as an image the model can look at; a model without image input gets a notice instead. (Chat Completions tool messages hold text only, so there the images follow the tool results as a user message.)
- `write`: create or replace a file; creates missing parent directories.
- `edit`: exact unique replacements with `edits: [{"oldText":"…","newText":"…"}]`; overlapping edits are rejected.
- `bash`: execute a command in the project directory; reports output and failure exit status.
- `webfetch`: fetch HTTP(S) content, converting basic HTML to Markdown. Follows up to three redirects, checking `webfetch` permission for each target URL, and decodes gzip/deflate responses; the 1 MiB limit applies to decoded bytes.
- `skill`: load the body of a discovered `SKILL.md` on demand. See [skills](skills.md).

Opt in to `zeta_inspect` with `"inspect_tool": true` in user, project, or profile config. It is a read-only view of zeta's live state for the project. With no arguments it returns a summary (counts and section names); `section` selects one of `plugins` (with discovered skills), `tools` (with prompt sections), `hooks`, `providers` (with apis), `commands`, `config` (effective values with each value's source layer, secrets redacted, plus diagnostics), or `diagnostics`. It reads the project's config without a session's model or profile overrides. The HTTP `/registry` and `/config` routes remain available without this setting.

Arguments are schema-validated. Reads may execute concurrently; writes, edits, and shell calls execute sequentially. Tool results are limited to 2,000 lines / 50 KiB. A longer result is saved in full beside the session log (`<data>/sessions/<project>/<session>.artifacts/<call>.txt`, deleted with the session, copied into a fork) and the model gets its start and end with the path; `read` can page through the session's own saved output with `offset` and `limit`, without an `external_directory` permission. Other sessions' files need that permission as usual. (`bash` and `read` already keep their own output within the limit.) Web responses and skill files have a 1 MiB input cap. The default timeout is 120 seconds (`tool_timeout_ms`). Tools run under [permissions](permissions.md). `write` and `edit` keep a copy of each file they change, so `zeta undo` (or `POST /sessions/:id/undo`) can put back the latest reply's changes; `bash` changes are not tracked.

The build-generated [reference](generated/reference.md) contains current built-in descriptions and input JSON Schemas taken from the tool definitions. `GET /registry?location=<absolute-project>` (or `?session=<id>`) reports the tools a run at that location gets (registered ones plus the skill tool), each with the plugin that provided it, along with providers and diagnostics. Built-in plugins sit in the built-in layer; a plugin in a narrower layer (user, then project) replaces a tool of the same name. Built-in tools must stay within the subset of JSON Schema zeta validates.

`zeta_inspect` returns the same data, split into sections. There is no tool for changing zeta's source (see [extending zeta](extending.md)).

## Hook points

Plugins can intercept a run at eight points, in the order a run reaches them: `session_start` (the session's first run in this server process: add context before its first prompt), `prompt_submit` (a prompt leaving the inbox: block it, or add context after it), `context_build` (replace the history the model sees; the log is unchanged), `provider_request` (replace the request, e.g. its system prompt), `tool_pre` (after a call's arguments pass the schema and before permissions: continue, rewrite the arguments, which are checked again, or block the call with a reason the model gets as an error result), `permission` (only where permission rules would ask: allow, optionally with new arguments, which must still pass the schema and every deny rule, deny with a reason the model gets, or leave it to the user), `tool_post` (replace the result, including the error result of a tool that failed), and `turn_stop` (when the agent would stop: stop, or continue with a user message; a continued stop cannot be continued again). Hooks run in load order (built-in, user, project), each seeing what earlier ones changed; the first block, answer or continue ends the chain. A failing `tool_pre` hook blocks the call, a failing `permission` hook denies it, a failing `turn_stop` hook lets the turn stop, and other failures are logged and skipped. The system prompt and tools logged for a request are the ones sent after `provider_request` hooks. `GET /registry` lists registered hooks; none ship built in.
